# AdminBot PostgreSQL cutover

This is a production gate, not an instruction to switch the live service today. The AdminBot service still constructs a SQLite path in `extensions/adminbot/host/main.ts`, and `extensions/adminbot/src/api/server.ts` opens `AdminBotSqliteStore`. Several batch scripts also open SQLite directly. Selecting a PostgreSQL URL without replacing and testing **every writer** would split or lose data. The separate OpenClaw gateway database and non-database state are outside this migration and must remain intact.

The staging auth adapter is not ready to serve registration approvals: `approveRegistration` still relies on a process-local guard and separately creates the member, credential, and decision. Two app instances could approve the same request, and a failed credential insert could leave an orphan signup member. Its credential insert currently upserts on member ID, which could overwrite a password during a replay. Make approval one database transaction with an atomic pending-to-approved claim and idempotent external effects before wiring PostgreSQL into a running service.

## Target and ownership

The 2026-09-24 read-only Aurora check found no installed PostgreSQL client/server, postgres account, PostgreSQL service, or listener on 5432/6432. The active AdminBot SQLite database and its retained point-in-time copy are on the same NFS4 volume. Aurora has local ZFS, but its parent is root-owned and the current account cannot provision a private dataset. Neither the current NFS directory nor a temporary local directory is an approved PostgreSQL data directory.

The active `jinesis-adminbot.service` opens the live ledger. The OpenClaw gateway can trigger writes through the API. A readable OpenClaw cron database lists two enabled hourly email jobs (`adminbot-email` and the older `adminbot-email-automation`) plus `adminbot-meeting-artifacts`, but that database's last-run times stopped on 2026-09-20; it is **not proven** to be the active gateway's cron store. The deployed job manifest also contains both email variants. Verify the owner-private gateway cron store before cutover, then stop every active email and meeting writer. The email job opens SQLite directly; the meeting job now uses the SQLite service store for both meetings and artifact tracking, so it still needs a PostgreSQL service path. The reference-verdict cache also uses `DatabaseSync`, but the deployed AdminBot database does not contain its table, so confirm its configured path before including it. Manual seed, import, and backfill scripts can write the ledger too. A service-unit list alone does not enumerate these writers.

Ask the service/data owner and CSLab/ITS to choose and approve **one** durable target:

1. Prefer a dedicated [ITS Private Cloud](https://its.utoronto.ca/its-units/eis/) VM with locally attached durable storage and an agreed PostgreSQL operator/backup contract, or a U of T-approved [Azure Database for PostgreSQL Flexible Server](https://learn.microsoft.com/en-us/azure/postgresql/security/security-overview) reached over private networking. ITS documents IaaS and Azure hosting; it does **not** promise a managed PostgreSQL instance for this application. Confirm the route from the AdminBot service before choosing Azure.
2. A private child dataset on Aurora's local ZFS is an interim self-managed option only if the host owner provisions it and approves this workload, access, quota, encryption, monitoring, and off-host backup. Do not run PostgreSQL data files on the current NFS4 volume.

Record the data classification, named database and backup operators, budget, recovery point objective (RPO), recovery time objective (RTO), retention, and where encrypted off-host copies live. U of T's [classification standard](https://security.utoronto.ca/governance/standards/data-classification-standard/) and [resilient-backup guideline](https://security.utoronto.ca/governance/guidelines/guideline-on-resilient-backups/) govern those choices. The current same-volume SQLite snapshot is useful for one-file recovery, but does not meet an off-host recovery objective.

## Initial configuration to test

Ten thousand registered members are not ten thousand concurrent database connections. Benchmark real request mixes and peak concurrency before sizing further. For a **dedicated** starting allocation of roughly 2 vCPU, 4 GiB RAM, and expandable SSD storage, use a supported PostgreSQL release and start with `max_connections=100`, `shared_buffers=512MB`, and the default `work_mem=4MB`; leave autovacuum enabled. Reserve disk for data, indexes, WAL, and restore headroom. These are trial settings, not a capacity claim. In particular, do not calculate `shared_buffers` from Aurora's shared 1.5 TiB host RAM: [PostgreSQL's memory guidance](https://www.postgresql.org/docs/current/runtime-config-resource.html) is for memory allocated to a database server, and `work_mem` can be consumed by several operations in each concurrent query.

Use a small, bounded application pool initially (for example, 5–10 connections per process), then adjust from active connection, queue-wait, CPU, I/O, and p95 latency measurements. Count **all** app replicas and jobs against the server limit. Add PgBouncer if connection churn or multiple replicas actually exhaust the pool; if using Azure, its [built-in PgBouncer](https://learn.microsoft.com/en-us/azure/postgresql/connectivity/concepts-pgbouncer) is available on supported tiers. Do not create one PostgreSQL backend per signed-in browser.

Keep the database on a private network, allow only application/operator sources, require TLS with server-certificate verification for TCP clients, and store credentials in the approved host secret store. Use separate least-privilege roles for the application, schema migration, and backup; the app must not be a superuser or schema owner. Never put a database URL, credentials, member rows, or raw query parameters in Git, CI logs, screenshots, or PR evidence. PostgreSQL supports [TLS configuration](https://www.postgresql.org/docs/current/ssl-tcp.html); Azure Flexible Server supports [private access](https://learn.microsoft.com/en-us/azure/postgresql/network/concepts-networking-private).

Enable aggregate query/connection metrics and alerts for saturation, errors, disk, WAL/archive lag, and backup failures. Investigate slow queries with `EXPLAIN (ANALYZE, BUFFERS)` on synthetic or approved isolated data before adding indexes. Avoid blanket memory or connection increases to mask full-table scans.

For a reproducible comparison, keep the same fictional dataset and request mix for SQLite and PostgreSQL. A local SQLite baseline on 2026-09-24 used 10,005 synthetic members, 200 requests per route at concurrency 20, and `scripts/load-test-adminbot.mjs`: `/auth/session` p95 11.1 ms, first member page p95 12.6 ms, and a deep member page p95 12.1 ms. Thirty sequential logins had p50 25.5 ms and p95 29.3 ms. This is a warm local SSD fixture, **not** Aurora/NFS latency or a PostgreSQL result; the comparison is incomplete until the same fixture runs through the PostgreSQL service. Record CPU, pool wait, query timings, response sizes, and errors alongside p50/p95 rather than attributing every change to the database.

A separate local PostgreSQL 16 import of the same fictional 10,005-member roster used the name index for the first 50 rows (`EXPLAIN ANALYZE`: 0.424 ms execution); an offset-5,000 page took 16.7 ms. These are database-query timings only, not end-to-end request measurements or evidence that the deployed UI improved. Revisit offset pagination if deep-page latency grows with actual usage.

## Backup and restore gate

Before any production import, establish encrypted, access-controlled **off-host** backups, a retention schedule approved by the data owner, and point-in-time recovery (PITR) through base backups plus continuous WAL archiving or the managed service's equivalent. A `pg_dump` can provide a portable extra copy but is not by itself PITR. See [PostgreSQL's PITR procedure](https://www.postgresql.org/docs/current/continuous-archiving.html) and [Azure Flexible Server backup/restore limits](https://learn.microsoft.com/en-us/azure/postgresql/backup-restore/concepts-backup-restore).

Restore a new, isolated PostgreSQL instance from the chosen **off-host** backup, recover to a recorded timestamp, and verify table counts, canonical per-table digests, constraints, sequences, and application read-only smoke tests. Record backup time, checksum, restore duration, achieved RPO/RTO, and operator sign-off without recording row contents. Do this before cutover, after material backup changes, and on the agreed recurring schedule. A local snapshot alone does not pass this gate.

## Cutover gates

Proceed in a maintenance window only when each gate below has a recorded pass and an owner:

1. **Software:** The PostgreSQL store implements the same authorization, sessions, proposal/approval/execution idempotency, audit, and search behavior as SQLite. The API, sheet poller, cron jobs, import/backfill tools, and every direct SQLite writer have been inventoried and either ported or disabled for the cutover. A configured PostgreSQL connection must fail closed if unavailable; it must never fall back to a new empty SQLite file. Synthetic parity, concurrency, and load tests pass at the agreed peak request rate.
2. **Target:** The owner approves the host, data classification, network/TLS, roles, capacity, monitoring, and off-host backup/PITR. The isolated restore drill above passes. Record the exact old release, new release, schema versions, and rollback operator.
3. **Freeze:** Put the UI/API in maintenance or read-only mode. Stop the AdminBot API, gateway actions, sheet poller, cron/timers, and manual/import writers; verify that no process can write the SQLite file. A systemd unit list alone does not establish this. Disable external action execution during verification so a replay cannot send a second message or email.
4. **Final source:** With writers quiesced, take a SQLite-consistent final snapshot using SQLite's backup API or `VACUUM INTO` (never a bare copy of a WAL-mode `.sqlite` file). Run `PRAGMA integrity_check`, record schema/table inventory, row counts and canonical digests, seal its checksum, and leave the original state directory and required non-database state untouched for rollback. Copy the verified snapshot to the approved protected backup destination.
5. **Import:** Load that one frozen snapshot into a fresh PostgreSQL database/schema. Reject partial imports. Verify every table and row count, canonical digests for all records, foreign keys/uniqueness, sequence next values, and security-sensitive records (sessions, approvals, execution/idempotency, audit) without printing private values. Resolve any mismatch **before** switching the service.
   The importer rejects duplicate pending email/member claims and installs partial unique indexes in PostgreSQL even when the frozen SQLite version predates those indexes.
   The rehearsal importer leaves a staging schema in place if read-back verification fails after its import transaction commits. Treat it as **unverified** and never promote it. Diagnose the mismatch and manually remove only that fresh staging schema once its evidence is recorded; a pre-commit import failure rolls back schema creation.
   The retained source has NUL characters in two declared SQLite text keys: `adminbot_cv_changes.entry_key` and `adminbot_feedback.id`. PostgreSQL text cannot hold NUL, so the importer preserves their UTF-8 bytes as `bytea`; the runtime store must encode and decode both consistently before this gate can pass.
6. **Read-only smoke:** Point the new release at PostgreSQL with writes and connectors still disabled. Confirm startup uses only the intended database; the signed-in dashboard and representative member/admin pages load; unauthenticated and unauthorized routes still deny; paper, availability, meetings, and search results match the frozen source. Check error, connection, pool, CPU, and query-latency metrics. Do not reopen traffic on a mismatch.
7. **Open:** Switch the single production writer to PostgreSQL, enable the API/gateway and jobs once, then admit writes. Record the first accepted write time. Monitor database health, p95 request latency, error rate, audit continuity, and external-action idempotency. Keep the sealed SQLite source untouched until the retention decision is approved.

## Rollback boundary

Before the first PostgreSQL-only write, stop the new service and jobs, verify the SQLite source has not changed, and switch back to the recorded old release and source if the owner accepts the existing SQLite-on-NFS risk. Once **any** PostgreSQL write or external action is accepted, that source is stale: never just flip the URL back or restore its old snapshot. Freeze writes again; recover the PostgreSQL target from PITR or reconcile and verify a reverse delta, including audit/idempotency and any external effects, before reopening. If that cannot be proved, keep the service read-only and escalate to the owner. Do not silently drop writes to meet an RTO.
