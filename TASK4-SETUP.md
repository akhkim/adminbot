# Task 4 local setup — concurrent request resilience and fallback

Local development scaffolding for **Task 4: Concurrent Request Resilience and Fallback** —
queuing and load shedding around the LLM calls, because the lab has 100+ members and inference
runs on a single GPU.

Two scripts, both under `openclaw-adminbot/scripts/`:

| Script | What it is |
| --- | --- |
| `adminbot-fixture-db.ts` | Generates a throwaway `adminbot.sqlite` at production scale, full of obviously-fake data. |
| `adminbot-mock-local-model.mjs` | Stands in for the vLLM server at `http://127.0.0.1:8000/v1`, with controllable concurrency, latency and failure modes. |

## No production data is used

Nothing here reads, copies, or connects to the runtime bundle, its WhatsApp session, its gateway
env file, or its database. Every roster row, paper, proposal and model reply is generated by these
two scripts.

- Every generated address is on an RFC 2606 / RFC 6761 reserved domain (`example.com`,
  `example.org`, `example.invalid`). None of them resolve; none can be registered.
- Every generated name is `Test Member NNN` — deliberately not a plausible human name, so nobody
  reading a log line or a screenshot has to work out whether they are looking at real people.
- Every generated member has `receives_nudges: false`, so a sweep run against the fixture cannot
  address anyone even before the addresses are considered.
- Every generated execution row is `dry_run: true` / `status: "simulated"`. The fixture never
  claims an external effect happened.
- The generator **refuses** to write under `~/.openclaw/`, under the repo's `state/`, or into any
  path containing `runtime-bundle`.

## Prerequisites

Node 22.19+ and pnpm through corepack, per the repo's own requirements.

```bash
cd openclaw-adminbot
corepack pnpm install --frozen-lockfile
pnpm build
```

Neither script below needs `pnpm build` — the mock server is dependency-free and the fixture
generator runs through `tsx` — but the build is what the repo's verification checklist starts with.

## Fixture generator

Dry run by default, following the house pattern from `adminbot-seed-member-passwords.ts`. It
prints what it would write and touches nothing; `--write` is the only thing that commits.

```bash
cd openclaw-adminbot

# See what it would create (roster mix, sample rows) without writing.
node --import tsx scripts/adminbot-fixture-db.ts

# Create it. Default target is .artifacts/adminbot-task4/adminbot-fixture.sqlite (gitignored).
node --import tsx scripts/adminbot-fixture-db.ts --write

# Custom scale and a different seed.
node --import tsx scripts/adminbot-fixture-db.ts --write --members 400 --papers 80 --seed 7

# Overwrite an existing fixture.
node --import tsx scripts/adminbot-fixture-db.ts --write --force
```

| Flag | Default | Meaning |
| --- | --- | --- |
| `--write` | off | Actually create the database. |
| `--members <n>` | `160` | Roster size. The live roster is 159. |
| `--papers <n>` | `40` | Paper records. |
| `--proposals <n>` | `24` | Proposals, each with one execution row and two audit events. |
| `--seed <n>` | `1` | PRNG seed. Same seed produces a byte-identical database. |
| `--force` | off | Overwrite an existing file (and its stale `-wal` / `-shm` siblings). |

The schema is never restated in the script: `new AdminBotSqliteStore(path)` runs the real
`CREATE TABLE` statements from `extensions/adminbot/src/persistence/sqlite.ts`, and the rows go in
through the real store methods. A fixture therefore cannot drift from the schema the service reads
— all 44 tables are created.

Point the service at it with the usual path argument, or by copying it where the service expects.

## Mock local-inference server

Impersonates vLLM's OpenAI-compatible API. Loopback only by default, because every caller in this
tree asserts the endpoint is loopback before it will send anything (`assertLoopbackModelUrl` in
`extensions/adminbot/src/cv-scan.ts`, `assertLoopbackUrl` in
`extensions/adminbot/src/guidebook/local-client.ts`).

```bash
cd openclaw-adminbot

# Defaults mirror production: port 8000, concurrency 2 (vLLM --max-num-seqs 2).
node scripts/adminbot-mock-local-model.mjs

# A saturated, slow server that sheds anything past a two-deep queue.
node scripts/adminbot-mock-local-model.mjs --concurrency 2 --latency-ms 4000 --queue-limit 2

# A server that 503s half the time, after the first 10 requests succeed.
node scripts/adminbot-mock-local-model.mjs --fail-mode 503 --fail-rate 0.5 --fail-after 10

# Record every request as NDJSON for later assertions.
node scripts/adminbot-mock-local-model.mjs --log /tmp/model-requests.ndjson
```

Then point the app at it — this is already the default, so usually nothing to set:

```bash
export ADMINBOT_LOCAL_BASE_URL=http://127.0.0.1:8000/v1
```

### Routes

- `GET /v1/models`
- `POST /v1/chat/completions` — streaming and non-streaming
- `POST /v1/embeddings` — deterministic vectors, because `guidebook/local-client.ts` calls it

Paths also work without the `/v1` prefix, so a health check that appends its own path still finds
the endpoint rather than a 404 that reads like a broken server.

The reply honours `response_format.json_schema` by generating a minimal instance of the schema.
`workshop-match-llm.ts` sends a strict schema and parses the reply against it; without this, a load
test against the mock would fail at the parse rather than at the queue, and would be measuring the
wrong thing.

### Load shape and failure injection

| Flag | Default | Meaning |
| --- | --- | --- |
| `--concurrency <n>` | `2` | Requests served at once. Matches the live `--max-num-seqs 2`. |
| `--queue-limit <n>` | unbounded | Queued requests tolerated beyond those. Unbounded is what vLLM does; set it to shed with 503 instead. |
| `--latency-ms <n>` | `600` | Service time once admitted. |
| `--jitter-ms <n>` | `0` | Uniform +/- jitter. Zero by default so a run is reproducible. |
| `--ttft-ms <n>` | `latency/4` | Time to first streamed chunk. |
| `--fail-mode <mode>` | `none` | `none` / `503` / `500` / `hang` / `econnreset` / `refuse`. |
| `--fail-rate <0..1>` | `1` | Fraction of requests the mode applies to. |
| `--fail-after <n>` | `0` | Serve this many normally first. |
| `--seed <n>` | `1` | Seeds the failure sampling, so the same victims fail on every run. |

The failure modes are deliberately distinct because a fallback layer should treat them differently:

- **`503`** — the server is up and refusing work. Back off and retry, or fall back.
- **`hang`** — accepted and never answered. Exercises the *client's* timeout; there is no response
  to react to.
- **`econnreset`** — the socket dies mid-flight.
- **`refuse`** — the listener closes, so connections get `ECONNREFUSED`. This is "the local model
  is not running", which is a different condition from 503 and should exercise a different branch.

### Control plane

The knobs can be changed mid-run, so one load test can move a server from healthy to saturated to
absent without restarting and losing its counters.

```bash
curl -s 127.0.0.1:8001/__stats | jq
curl -s 127.0.0.1:8001/__requests | jq
curl -s -XPOST 127.0.0.1:8001/__control -d '{"concurrency":1,"latencyMs":5000}'
curl -s -XPOST 127.0.0.1:8001/__control -d '{"failMode":"refuse"}'   # take it down
curl -s -XPOST 127.0.0.1:8001/__control -d '{"failMode":"none"}'     # bring it back
curl -s -XPOST 127.0.0.1:8001/__reset
```

The control plane gets **its own listener** on `--control-port` (default `port + 1`). It has to:
`refuse` is implemented by closing the model listener, so serving `/__control` from that same
socket would make the mode a one-way door — the test turns the server off and then cannot turn it
back on. The routes are also mounted on the main port for convenience, and that copy goes away
with the listener during `refuse`.

### The number that matters

`/__stats` reports two different concurrency peaks, and the distinction is the point:

```json
"concurrency": {
  "peak_served": 2,
  "peak_arrivals": 50,
  "peak_queue_depth": 47
}
```

- `peak_served` is capped at `--concurrency` by construction. A client with a working queue and a
  client with none look **identical** here, so it proves nothing about the client.
- `peak_arrivals` is the number of requests received and not yet answered — queued ones included.
  That is the client's own in-flight count, observed from the other end of the socket.

So the assertion a queue layer should be tested against is on `peak_arrivals`, not `peak_served`.
A run that fires 50 requests and reports `peak_arrivals: 50` has no client-side limit at all,
whatever `peak_served` says.

`distinct_fingerprints` and `duplicate_fingerprints` cover the other half: a fingerprint is the
hash of the semantic payload (model + messages + decoding knobs), not the raw bytes, so a retry
that re-serializes the same object with keys in a different order still counts as a duplicate.
That is what a test asserting "the queue did not send this prompt twice" needs.

Request logs record a `prompt_preview` (120 chars) rather than the whole prompt. This mock will
eventually be pointed at a real workflow by someone debugging, and a full transcript of every CV
and receipt prompt sitting in an NDJSON file is a liability nobody asked for.

## Worked example

```bash
cd openclaw-adminbot

node --import tsx scripts/adminbot-fixture-db.ts --write --force
node scripts/adminbot-mock-local-model.mjs --concurrency 2 --latency-ms 1500 --queue-limit 4 &

# ... drive the app ...

curl -s 127.0.0.1:8001/__stats | jq '.concurrency, .counters'
```

`counters.shed_503` is how many requests the server turned away; `concurrency.peak_arrivals` is
how many the client had outstanding at its worst moment. A working queue and fallback layer should
move the first toward zero and hold the second at whatever limit it claims to enforce.
